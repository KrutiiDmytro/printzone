# План: капітальний фікс прав деплою (root-owned файли у bind-mount)

> **Статус:** до реалізації. Окрема задача, не блокує — щоденний деплой уже працює завдяки
> самовідновленню (MR !7). Гілка (запропонована): `fix/deploy-perms-rootcause`.

## Context (навіщо)
Під час першого прод-деплою сервісів `rsync` упав із `mkstemp ... Permission denied (13)` у
`/var/www/app/public/`. Тимчасово закрито в MR !7 (chown `public/` через root-контейнер **перед**
кожним rsync — ідемпотентний пластир). Це лікує наслідок, але не причину: при кожному деплої
проблема відтворюється й «лагодиться» наново, а захист звужений лише до `public/`.

**Першопричина (з розвідки коду):** у синхронізоване дерево `/var/www/app` пишуть **два актори з
різними власниками**:
- **runner** (неприлегований) — крок `rsync` у джобі `deploy` (`.gitlab-ci.yml`);
- **контейнери від root** — `php`/`worker` (моноліт) і сервісні контейнери виконують
  `composer install`, `bin/console …`, `assets:install` тощо як **root** (`Dockerfile.php`:
  `FROM php:8.2-fpm`, без `USER`; prod-compose маунтить `.:/var/www/html`, без `user:`).

Коли контейнер створює/чонить файли чи каталоги в bind-mount як root, неприлегований rsync
наступного деплою не може там створити тимчасовий файл → `mkstemp` Permission denied.

**Бажаний результат:** дерево деплою має єдиного власника (runner); контейнери не залишають
root-owned артефактів у синхронізованих шляхах. Деплой перестає залежати від пластиря.

## Рекомендований підхід — вирівняти UID контейнерів з runner'ом
Запускати `php`/`worker` (та сервісні контейнери, що пишуть у bind-mount) **від UID/GID runner'а**,
щоб усе, що вони пишуть у дерево, належало runner'у. Тоді rsync завжди має право запису.

### Кроки
1. **Визначити UID/GID runner'а** і прокинути в compose як змінні. У джобах деплою (`.gitlab-ci.yml`)
   експортувати:
   ```
   export DEPLOY_UID=$(id -u); export DEPLOY_GID=$(id -g)
   ```
   (Docker Compose підхопить їх для інтерполяції; на проді — це й буде власник `/var/www/app`.)
2. **`compose.prod.yaml` (моноліт):** додати до `php` і `worker`:
   ```yaml
   user: "${DEPLOY_UID:-1000}:${DEPLOY_GID:-1000}"
   ```
   Перевірити, що php-fpm стартує не-root (pid/socket-каталоги writable; за потреби — pool
   `listen.owner`/власний `/tmp`). nginx віддає статику read-only — йому root ок.
3. **Сервісні `compose.prod.yaml` (catalog/user):** FrankenPHP слухає `:80` → не-root не зв'яже
   привілейований порт без `CAP_NET_BIND_SERVICE`. Варіанти: (а) лишити сервіси як є (вони **не**
   пишуть у монолітний `public/` — проблема не в них), (б) `SERVER_NAME=":8080"` + `cap_add:
   [NET_BIND_SERVICE]` або порт >1024 і запуск від `DEPLOY_UID`. **Рекомендація:** у цьому кроці
   чіпати лише моноліт (джерело інциденту), сервіси — за потреби окремо.
4. **Одноразовий бекфіл власності** на проді (root-owned спадок від попередніх деплоїв) — через
   root-контейнер (як у MR !7), але на все дерево, один раз:
   ```
   docker run --rm -v "$DEPLOY_DIR:/app" busybox chown -R "$DEPLOY_UID:$DEPLOY_GID" /app
   ```
5. **Прибрати/спростити пластир MR !7** після верифікації (або лишити як дешеву страховку —
   обговорити). Якщо лишаємо — розширити з `public/` на весь `$DEPLOY_DIR` про всяк випадок.

### Альтернатива (якщо UID-вирівнювання виявиться крихким)
Дзеркалити патерн сервісів на моноліт: винести `vendor/`, `var/`, `public/assets`, `public/bundles`
у **named-volumes**, щоб контейнери писали не в bind-mount, а в томи. Тоді в синхронізованому дереві
пише лише runner → конфлікту власності немає. Більший обсяг змін і ризик (треба `assets:install`/
`importmap` спрямувати в томи), тому як план Б.

## Критичні файли
- `.gitlab-ci.yml` — джоба `deploy` (export UID/GID; бекфіл; пластир MR !7), за потреби
  `deploy:catalog-service`/`deploy:user-service`.
- `compose.prod.yaml` (моноліт) — `user:` для `php`/`worker`.
- `Dockerfile.php` — за потреби підготувати образ до не-root (права на `var/`, php-fpm pool).
- `services/*/compose.prod.yaml` — лише якщо вирішимо вирівнювати й сервіси (крок 3б).

## Ризики
1. **php-fpm не-root** — pid/socket/`/tmp` мають бути writable; інакше контейнер не підніметься.
   Верифікувати локально перед прод-деплоєм.
2. **FrankenPHP + привілейований порт** — головна причина НЕ чіпати сервіси в цьому кроці.
3. **Бекфіл chown** — важка рекурсія по `vendor/` (метадані); одноразово прийнятно.
4. **Регресія деплою** — змінюємо рантайм-користувача; обов'язково повний прогін pipeline на
   `develop` + перевірка `about`/health моноліту й вітрини.

## Verify (E2E)
1. Локально: `docker compose -f compose.yaml -f compose.prod.yaml` з `DEPLOY_UID/GID` →
   `php` стартує не-root, `bin/console about` ок, вітрина рендериться.
2. Прод-pipeline на `develop`: джоба `deploy` проходить rsync **без** пластиря (тимчасово вимкнути
   для перевірки), `php`/`worker` живі, health зелений.
3. Перевірити на хості: нові файли, створені контейнерами (`var/`, `public/assets`), належать
   `DEPLOY_UID` (`ls -la`), а не root.
4. Повторний деплой поспіль — другий rsync не падає (доказ, що причину усунено, не лише наслідок).
